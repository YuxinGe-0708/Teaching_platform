# 单体版与微服务版性能对比实验报告

## 1. 实验目的

对比改造前单体版与改造后微服务版在相同机器、逻辑等价测试数据和同一份 HTTP 压测脚本下的性能表现。实验不预设微服务版本一定更快，所有结论仅依据本次保留的原始测试记录。

## 2. 对比版本

| 对象 | 代码版本 | 访问入口 | 说明 |
| --- | --- | --- | --- |
| 单体版 | `e7e32cc`，`baseline-e7e32cc` | `http://localhost:8081` | 改造前单体后端入口 |
| 微服务版 | `dff546e`，`dev_dockerfile` | `http://localhost:3000` | 改造后统一入口，包含网关/BFF 到业务微服务的调用链 |

## 7. 对比分析

1. **登录场景接近。** 微服务版吞吐量比单体版低约 `4.2%`，平均响应时间高约 `4.4%`，P95 高约 `10.3%`。认证请求在微服务版本中需要经过统一入口以及服务转发，增加了少量网络和序列化开销。
2. **课程详情场景单体版更快。** 微服务版吞吐量低约 `47.3%`，平均响应时间约为单体版的 `1.92` 倍，P95 约为 `1.89` 倍。该场景的微服务链路多出网关/BFF 转发以及可能的服务间调用，读取路径更长。
3. **编程判题场景差异最大。** 微服务版吞吐量约为单体版的 `1/27.47`，平均响应时间和 P95 显著升高。微服务版中的判题请求经过入口层、assessment-service 和本地判题链路；多个容器启动后的资源竞争、服务调用及进程调度开销会在计算型请求中更明显。
4. **本次不能写“性能提升”。** 三个代表性接口的实测结果均显示当前单体版整体更快；微服务化的主要收益在于业务边界、独立部署和扩展能力，而不是在当前单机、低并发参数下必然降低单请求延迟。

## 9. 判题场景的有效性说明

最初携带 `taskId` 对同一学生和同一任务进行并发提交时，单体版会因重复写入同一提交记录触发 `TooManyResultsException`，无法得到两个版本都成功的可比结果。为保证两版使用**相同压测脚本、相同请求体和相同并发条件**，本次正式实验使用 `-NoJudgeTaskId`，即向 `POST /api/v2/judge/submit` 发送不携带 `taskId` 的固定 Python 代码。

因此，第 5 至第 7 节中“编程判题”指标代表的是**判题计算链路的性能**，不代表并发创建提交记录、事务写入与成绩持久化的性能。若后续需要比较“带任务 ID 的提交持久化”性能，应先在两个版本中统一实现幂等提交策略或使用不同测试账号/任务 ID，避免重复写入语义影响测试结果。
